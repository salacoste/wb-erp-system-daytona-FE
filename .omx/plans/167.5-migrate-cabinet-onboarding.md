## Risks and Mitigations

- **Shared-file collision:** enforce the Allowed/Forbidden lists and route any shared need to its upstream owner.
- **Visual refactor changes behavior:** establish behavior-lock tests first and compare query, URL, formatting, calculation, focus, and state evidence.
- **Responsive or accessibility information loss:** verify semantic reading order, keyboard/touch access, non-color meaning, full-value access, and deliberate table/chart narrow-width behavior.
- **Duplicate create after partial success:** disable automatic mutation retry and hard-block another
  create when the service reports that POST succeeded but token refresh failed.
- **Direct native submit while work is pending:** recheck the current phase inside the submission
  path itself so bypassing a disabled button cannot start a second non-idempotent POST while the
  first POST is pending or restart create while the dependent margin PUT is pending.
- **Reload reopens non-idempotent create:** enter a `restoring` phase before enabling creation and
  persist only version/phase plus the minimum non-secret current-user discriminator in
  `sessionStorage`; clear mismatched-user and active-cabinet markers, and recheck the marker inside
  `onSubmit` so native-submit bypass cannot issue another POST. No token, password, cabinet ID,
  form value, cabinet payload, or email is persisted.
- **Auth-persistence split after committed create:** snapshot the current user/cabinet before POST,
  inspect fresh `useAuthStore.getState()` after failure, and classify a newly emerged live cabinet
  ID for the same user as committed/uncertain partial success even when Zustand throws a raw
  storage error. Keep only the exact minimal `{ version, phase, userId }` session marker plus the
  uncertain cabinet identity in module memory for the current JavaScript realm; same-realm remount
  and hard reload remain fail-closed, while genuine cabinet reconciliation and a different user
  clear the block. Raw pre-create failures with no newly emerged cabinet ID remain retryable.
- **False partial-success classification:** retain message-based post-create token recovery for the
  existing proven path, but do not let it override the higher-priority newly emerged cabinet-ID or
  margin-recovery classifications. Ordinary pre-create token expiry remains visible and deliberately
  retryable without writing a recovery marker.
- **Hydration overwrites recovery input:** model the create workflow phase explicitly and suppress
  cabinet-detail resets after create begins; prove stale/null GET data cannot replace the submitted
  margin before update-only recovery.
- **Stale worktree base:** create the worktree only after prerequisites merge and record the base SHA.
- **Repository clutter:** Story completion is blocked until remote/local feature branches and `/private/tmp/wb-fe-167-5-migrate-cabinet-onboarding` are absent.
