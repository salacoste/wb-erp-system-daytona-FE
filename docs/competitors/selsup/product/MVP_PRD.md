# MVP PRD — конкурент SelSup (Wildberries + Ozon, базовый цикл селлера)

> Actionable-постановка для старта разработки. Скоуп MVP вырезан «безжалостно»:
> только два маркетплейса (WB, Ozon) и только базовый цикл селлера. Всё остальное
> явно вынесено в post-MVP (раздел 11).
>
> Grounding: каждый ключевой элемент ведёт к конкретному артефакту комплекта
> `product/` (PRD.md, FEATURE_MAP.md, DATA_MODEL.md, WORKFLOWS.md, INTEGRATIONS.md,
> `specs/*`). Ссылки в формате `[файл §раздел]`.

---

## 1. Executive summary

**Что строим.** SaaS-сервис для селлера маркетплейсов — «единое окно» для управления
товарами, ценами, остатками, заказами и отгрузками. Архитектурно повторяем ядро
SelSup: **единый внутренний PIM-справочник товаров**, не зависящий от площадки;
карточка создаётся один раз и публикуется на маркетплейсы через «тумблеры-курки»
`[product-cards §Назначение]` `[DATA_MODEL §Обзор]`.

**Скоуп MVP.** Только **Wildberries + Ozon**, только **базовый цикл FBS-селлера**:

```
онбординг/организация → каталог/карточки → публикация на WB/Ozon
→ склад/остатки FBS → цены → заказы/сборка FBS → маркировка/этикетка
→ отгрузка (поставка FBS) → базовая аналитика/финансы
```

**Цели продукта (MVP):**
1. Дать селлеру на WB+Ozon управлять каталогом, ценами и остатками из одного
   интерфейса вместо двух ЛК (устранить «двойной ввод»).
2. Полностью провести FBS-заказ от импорта до закрытия поставки с печатью этикеток.
3. Показать базовый P&L (выручка, себестоимость, комиссия, прибыль) по двум МП.
4. Доказать надёжность синхронизации остатков/цен/заказов (key risk всего продукта).

**Главные non-goals MVP** (явно за пределами — см. раздел 3 и 11):
- любые маркетплейсы кроме WB и Ozon;
- AI-модули (Формализатор, фото/видео/SEO, AI-Стратегии, Точные поставки, Финдир);
- 1С / МойСклад / СБИС / CommerceML;
- закупки, производство, комплекты, 3-режимная FIFO-себестоимость;
- CRM (чаты/вопросы/отзывы), рекламные кампании, воронка, позиции в выдаче;
- репрайсер (контроль МРЦ, ночной), работа с акциями WB/Ozon;
- FBO-поставки на склады МП (полный цикл отгрузки на склад МП);
- DBS/realFBS, Express, опт/розница, дропшиппинг, B2B, КГТ;
- браузерное расширение, Telegram-бот, мобильные приложения;
- тарифы/оплата/партнёрская программа (внутренний биллинг — post-MVP).

> Полную карту 16 модулей и 608 возможностей SelSup см. в `[FEATURE_MAP]`;
> MVP берёт ~6 из них в урезанном виде.

## 2. Целевой пользователь и Jobs-to-be-Done

**Целевой пользователь MVP** — селлер-владелец малого/среднего бизнеса (ИП/ООО),
продающий одновременно на Wildberries и Ozon по схеме **FBS** (товар на собственных
складах), 1–10 сотрудников, от сотен до десятков тысяч SKU. Аналог ролей из
`[onboarding-account §capabilities 23–28]`: Администратор, Менеджер товаров,
Сотрудник склада, Управление ценами.

**JTBD (Jobs-to-be-Done) MVP:**

1. **JTBD-1 (Каталог):** «Создать товар один раз и опубликовать его на WB и Ozon,
   чтобы не заполнять две карточки вручную» → PIM + тумблеры публикации
   `[product-cards WF-1]`.

2. **JTBD-2 (Остатки):** «Видеть и управлять остатками своих складов так, чтобы
   они автоматически передавались на оба МП и не было расхождений» → склад FBS +
   синхронизация `[stocks-inventory WF-1, WF-2]`.

3. **JTBD-3 (Цены):** «Назначать и обновлять цены на WB и Ozon из одного места,
   с защитой от продажи в минус» → единая таблица цен + минимальная цена
   `[prices-strategies WF-2]`.

4. **JTBD-4 (Заказы/сборка):** «Получать FBS-заказы с обоих МП, собирать их и
   отгружать, печатая нужные этикетки — не переключаясь между ЛК» → цикл сборки
   FBS `[orders-assembly WF-1]`.

5. **JTBD-5 (Финансы):** «Понимать, сколько я реально зарабатываю на каждом МП
   после комиссий и логистики» → базовый P&L `[analytics-finance]` (урезанно).

| Адресное хранение (ячейки, ТСД, раскладка, маршрутизация) | Сложный складской слой; MVP работает с «плоским» складом (без ячеек) `[stocks-inventory §Адресное хранение]`. |

## 4. MVP user journeys (end-to-end)

Журнеи взяты из `[WORKFLOWS]` и урезаны до MVP-скоупа.

### Journey A — Онбординг и первый импорт `[WORKFLOWS WF-01]`
Регистрация (телефон+email) → мастер: выбор МП (WB) → вставка API-токена (статус
«Настроено») → «Импортировать товары» → фоновой импорт карточек → добавление
организации по ИНН → повтор для Ozon (Client-Id + ключ Admin).
**Exit:** в «Товары» есть импортированные карточки WB и Ozon, связи матчинга.

### Journey B — Создание/импорт карточки и публикация `[WORKFLOWS WF-02]`
«Товары → Создать товар» → выбор категории + связь с категорией WB/Ozon →
заполнение служебных параметров (бренд, страна, цены, габариты) → для одежды:
цвета/размеры (ШК авто) → фото drag&drop, главное фото → тумблер WB → Сохранить
(«Карточка отправлена») → тумблер Ozon + дозаполнение параметров → Сохранить.
Альтернатива: импорт из WB/Ozon с автоматическим матчингом по ШК/артикулу.

### Journey C — Склад FBS и перенос остатков `[WORKFLOWS WF-03]`
«Склад → Добавить склад» → связь со складами WB/Ozon (ID из ЛК) → объединение
дубликатов → перевод старых заказов «На сборку» (чтобы не резервировали) →
«Перенести остатки» (с WB/Ozon по API) → проверка «Сверкой остатков» → включить
«Синхронизировать остатки» + «Автоматический импорт заказов» → ночной импорт.

### Journey D — Цены `[WORKFLOWS WF-08]` (урезанно, без юнит-экономики/репрайсера)
«Цены» → выбрать МП → ввести цену (общий столбец или по-МП) → указать минимальную
цену (защита) → Сохранить (цена уходит на МП; для WB — скидка целым числом) →
проверить «Историю цен» (успех/ошибка). Массово — через Excel.

### Journey E — Получение заказа и сборка FBS `[WORKFLOWS WF-04]`
Автоимпорт FBS-заказа (раз в ~2 мин) → статус **Новый**, резерв остатка →
галочками «На сборку» (создаётся поставка) → «Загрузить этикетки» (WB: привязка к
поставке; Ozon: статус МП → «Ожидает доставки») → Лист сборки PDF + печать
этикеток → сборка товаров → «Отметить собранными» → **Собран** → «Проверить и
закрыть» поставку (для WB — сверка состава) → **Отправлен** → приёмка на МП →
**В пути**.

### Journey F — Маркировка/этикетка (MVP: только печать, без ЧЗ)
В ленте заказов: печать этикетки заказа МП (PDF) + товарной этикетки (браузер/PDF).
> Полный цикл Честного Знака (КИЗ, ввод/вывод из оборота, СУЗ, ЭЦП) — post-MVP
> (см. §10 риски: только для маркируемых категорий).

### Journey G — Отгрузка/закрытие поставки FBS `[orders-assembly WF-6]`
Все заказы поставки → Собран → «Поставки → Проверить и закрыть» (массово) →
статусы **Отправлен** (WB: QR-код поставки; Ozon/др. — внутренние поставки в
системе). > FBO-поставка на склад МП — post-MVP.

### Journey H — Базовая аналитика/финансы `[WORKFLOWS WF-17]` (урезанно)
Сбор операций WB/Ozon по API → дашборд: заказы, выручка, себестоимость, комиссия,
**валовая прибыль** (по МП и суммарно) → лента заказов (график, фильтры, Excel).
Без ABC, налогов, ДДС, плана/факта.

## 5. MVP функциональные требования (must-have)

Только must-have; каждое — измеримое. Трассировка к source-спеке в `[...]`.

### 5.1. Онбординг и организации `[onboarding-account]`
- **FR-O1.** Регистрация по телефону+email с подтверждением; вход логин/пароль;
  сброс пароля по email `[§cap 1, 11]`. SLA: регистрация ≤ 30 с.
- **FR-O2.** Мастер быстрого старта: выбор МП → настройка интеграции → запуск
  импорта; автозагрузка аналитики за 2 недели `[§cap 2]`.
- **FR-O3.** Организация: добавление по ИНН с автозаполнением, налоговый режим,
  юр. адрес, банковские реквизиты; правило **1 организация = 1 ключ API МП**
  `[§cap 16, 17]`.
- **FR-O4.** Сотрудники: ФИО, должность, логин/пароль, роль; RBAC по ролям
  (минимум 4: Администратор, Менеджер товаров, Сотрудник склада, Управление
  ценами) `[§cap 23, 24]`.
- **FR-O5.** Аудит: запись «кто/когда/что» для критичных операций (создание
  карточки, сборка заказа, изменение цены) `[§cap 28]`.
- **FR-O6.** Лимит сессий: не более 2 устройств на аккаунт `[§cap 13]`.

### 5.2. Интеграции WB + Ozon `[integrations-marketplaces]`, `[INTEGRATIONS]`
- **FR-I1.** Подключение WB: ввод API-токена (тип — не «Только чтение»); шифрование
  AES-256; статус «Настроено/Частично/Не настроено» `[§cap 1–3, onboarding §cap 37]`.
- **FR-I2.** Подключение Ozon: Client-Id + API-ключ (тип «Admin») `[INTEGRATIONS §Ozon]`.
- **FR-I3.** Уведомление о невалидном/просроченном токене с кнопкой «Перейти к
  настройкам» `[§cap 4]`.
- **FR-I4.** Тумблеры организации: «Синхронизировать остатки», «Автоматический
  импорт заказов» `[stocks §cap 11, 12]`.

### 5.3. Карточки товаров (PIM) `[product-cards]`
- **FR-P1.** Создание карточки: 3-уровневая модель (Модель→Цвет→Размер) и
  упрощённая (без вариаций) `[§cap 6, 15]`. Обязательные поля: бренд, страна
  производства, цены со/без скидки, габариты/вес `[WF-2]`.
- **FR-P2.** Параметры: служебные (SelSup) + параметры WB и Ozon (из справочников
  МП) с настраиваемой видимостью `[§cap 16, 17]`.
- **FR-P3.** Фото: загрузка drag&drop, привязка к цвету, выбор главного, отметка
  «значками» МП; автодобавление белого фона `[§cap 34]`.
- **FR-P4.** Штрихкоды: автогенерация на размер; пометка использования по МП
  `[§cap 59]`.
- **FR-P5.** Публикация тумблерами-курками на WB и Ozon с детальными ошибками по
  каждому МП `[§cap 3, 61]`. Лимит: учитывать WB ≤ 1000 новых карточек/сутки.
- **FR-P6.** Импорт карточек из WB/Ozon (быстрый — только новые; обычный —
  полные данные) с автоматическим матчингом по ШК/артикулу в единую карточку
  `[import-export]`, `[WF-2]`.
- **FR-P7.** Статусы: Актуален/Неактуален/Архив/Удалён; архивирование без
  удаления `[§cap 50–53]`.
- **FR-P8.** Массовое редактирование через Excel (выгрузка шаблона → правка →
  загрузка с отправкой на МП) `[§cap 43]`.

### 5.4. Склад и остатки FBS `[stocks-inventory]`
- **FR-S1.** Создание физического склада FBS (1 физический = 1 в системе);
  связь со складами WB/Ozon (ID склада из ЛК) `[§сущность Warehouse, WF-1]`.
- **FR-S2.** Перенос остатков с WB/Ozon кнопкой + приёмка (поступление) с
  закупочной ценой/доп. расходами `[§cap 47, 51]`.
- **FR-S3.** Ручное изменение остатка в таблице с отправкой на МП (тумблер
  «Обновлять на маркетплейсе») `[§cap 4]`.
- **FR-S4.** Синхронизация: автоотправка изменения остатка при заказе + проверка
  новых FBS-заказов раз в минуту + ночной импорт в 00:00 МСК `[§cap 11, 12, 14]`.
- **FR-S5.** Защитные пороги: минимальный остаток FBS (передаётся 0 ниже порога);
  «уменьшать остаток на N» `[§cap 17, 16]`.
- **FR-S6.** Операции: списание остатков (документ), перемещение между складами
  `[§cap 22, 23]`.
- **FR-S7.** История отправки остатков (хранение 3 мес): статус успех/ошибка,
  причина `[§cap 53]`.
- **FR-S8.** Просмотр остатков FBO по API (только WB/Ozon) — **только чтение/
  отображение**, без управления `[§cap 2, INTEGRATIONS §WB/Ozon]`.

### 5.5. Цены `[prices-strategies]`
- **FR-C1.** Единая таблица цен по WB/Ozon с фильтром по МП; общий столбец или
  по-МП `[§cap 1, 4]`.
- **FR-C2.** Отправка цены на МП: для WB — скидка целым числом (округление вниз);
  для Ozon — цена + минимальная цена `[§cap 31 особые режимы, INTEGRATIONS]`.
- **FR-C3.** Минимальная цена как защита: ниже минимума цена не отправляется;
  мин. цена только снижается `[§cap 11]`.
- **FR-C4.** Массовое изменение через Excel (экспорт/импорт) `[§cap 8]`.
- **FR-C5.** История цен: товар, старые/новые цены, источник, дата, статус
  (успех/ошибка), причина ошибки `[§cap 26]`.

### 5.6. Заказы и сборка FBS `[orders-assembly]`
- **FR-Z1.** Три режима импорта: автоматический (по событию API), ручной «Импорт
  заказов» (без изменения остатков МП), «Импорт с обновлением остатков». Первый
  импорт тянет заказы за 3 мес; «перезагрузить за неделю» `[§cap 1]`.
- **FR-Z2.** Лента заказов: фильтры (тип/период/МП/статус/склад), финансовые
  показатели, выгрузка в Excel `[§cap 3]`.
- **FR-Z3.** Статусная модель: Новый→На сборке→Собран→Отправлен→В пути→…
  Внутренние статусы до отгрузки на МП **не передаются**; после отгрузки —
  синхронизация `[§cap 26]`.
- **FR-Z4.** Сопоставление товара «символ в символ» (WB — по ШК, Ozon — по
  артикулу); несовпадение → заказ не импортируется, фиксируется ошибка `[§бизправила]`.
- **FR-Z5.** Массовое «На сборку» (создание/дополнение поставки FBS) `[§cap 7]`.
- **FR-Z6.** Получение этикеток заказа: фильтр «Без этикетки» → «Загрузить
  этикетки» (WB — привязка к поставке; Ozon — статус МП «Ожидает доставки»)
  `[§cap 8]`.
- **FR-Z7.** Лист сборки (PDF) + Лента заказов с печатью этикеток (заказа МП —
  PDF МП; товарной — браузер) `[§cap 9, 10]`.
- **FR-Z8.** Отметка собранными и закрытие поставки («Проверить и закрыть»,
  сверка состава для WB) `[§cap 19]`.
- **FR-Z9.** Возврат остатка после отмены/возврата (автоматический до сборки;
  ручной — кнопкой «Вернуть на остатки»/приёмкой) `[stocks §cap 25]`.

### 5.7. Маркировка/этикетки (MVP-минимум)
- **FR-M1.** Печать этикетки заказа МП (PDF, формат МП) `[orders-assembly §cap 8]`.
- **FR-M2.** Товарная этикетка (название, артикул, ШК, размер, бренд) через
  браузер/PDF; один редактируемый шаблон `[orders-assembly §сущность «Товарная
  этикетка»]`.
- **(Post-MVP)** Честный Знак: КИЗ, СУЗ, ввод/вывод из оборота, ЭЦП, УПД ДОП
  `[marking-labels]`.

### 5.8. Аналитика/финансы (MVP-минимум)
- **FR-A1.** Сбор сырых операций WB/Ozon по API (продажа/возврат/логистика/
  комиссия/штраф/хранение/…); резерв — ручной импорт отчётов `[analytics-finance]`.
- **FR-A2.** Базовый P&L на дашборде: выручка, себестоимость (= закупочная +
  доп. расходы), комиссия, логистика, **валовая прибыль** и маржинальность —
  по МП и суммарно, за выбранный период.
- **FR-A3.** Лента/график заказов (шт./руб., группировка по дням) `[orders-assembly
  §cap 3]`.

### 5.9. Сквозные нефункциональные требования
- **NFR-1.** Мультиарендность (Account → Organization → Warehouse) `[DATA_MODEL §Обзор]`.
- **NFR-2.** Все обмены с МП — через очередь фоновых задач с retry/backoff;
  аудируемы `[DATA_MODEL §6, Background Task/Audit]`.
- **NFR-3.** Шифрование ключей API (AES-256) `[onboarding §cap 37]`.
- **NFR-4.** Веб-интерфейс (браузер ПК); адаптив под планшет (mobile-apps — post-MVP).
- **NFR-5.** Локализация ru; валюта RUB; часовой пояс МСК.

## 7. Интеграции MVP — WB API и Ozon API

Основано на `[INTEGRATIONS §Маркетплейсы]`, `[integrations-marketplaces]`,
`[DATA_MODEL §Integration]`.

### 7.1. Общие принципы
- Токен/ключ привязан к организации; статусы «Настроить/Настроено/Частично»;
  ключи шифруются AES-256; уведомления о невалидных токенах `[§cap 1–4]`.
- Все обмены — через очередь фоновых задач с retry/backoff; направления обмена
  фиксированы в `[INTEGRATIONS]`.
- Один магазин — один аккаунт; повторное подключение того же магазина на другом
  аккаунте блокируется `[INTEGRATIONS §принципы]`.

### 7.2. Wildberries

| Аспект | Значение |
|---|---|
| **Аутентификация** | API-токен (заголовок `Authorization`). Тип — **не** «Только чтение». Срок действия ограничен → регулярная ротация. |
| **Публикация карточек** | Создание/редактирование карточек через API; матчинг по ШК; лимит ≤ 1000 новых карточек/сутки. |
| **Цены** | Отправляется **скидка целым числом** (округление вниз), не цена; «Со скидкой новая расчётная» — реально ушедшая; вкладка «Карантин» при слишком большой скидке. |
| **Остатки FBS/FBO** | Двусторонние по API; FBO — по API (чтение). FIFO-учёт на стороне системы. |
| **Заказы** | Импорт FBS/FBO по API; автоимпорт ~раз в 2 мин; глубина 3 мес («Джем» — вся история). |
| **Этикетки/поставки** | Этикетка заказа (PDF WB); привязка заказа к поставке; «Проверить и закрыть» со сверкой состава; QR-код поставки. |
| **Финансы** | Продажи/финансы — еженедельно/ежедневно; реклама «спрятана» в «прочие выплаты», даты сдвинуты на 1–3 дня. |
| **Ограничения** | Состав товаров в акциях/автоакциях — только в ЛК (не по API). Статусы/материалы **FBO-отгрузок по API НЕ передаются** (ручная связка через файл) → FBO-цикл = post-MVP. |

### 7.3. Ozon

| Аспект | Значение |
|---|---|
| **Аутентификация** | `Client-Id` + `Api-Key` (тип токена **«Admin»**). Дополнительно Ozon Performance (`client_id`/`client_secret`) — **post-MVP** (потоварная реклама). |
| **Публикация карточек** | Создание/редактирование; бренд **привязывается по числовому ID** (`ozon_id`), не создаётся по API. |
| **Цены** | Цена + **минимальная цена**; защита от ухода в минус. Репрайсер для Ozon временно НЕ поддерживается (API). |
| **Остатки FBS/FBO** | Двусторонние по API (включая FBO — чтение). Кластеры поставки/доставки для FBO. |
| **Заказы** | Импорт FBS/FBO; глубина 3 мес / Премиум 6 мес / Премиум+ — вся история. |
| **Этикетки/поставки** | Этикетка после статуса «Ожидает доставки»; **поставки Ozon — внутренние** (не создаются через API). **Заказ в Ozon создаётся один раз** и не редактируется. |
| **Маркировка** | Импорт кодов маркировки из Ozon (→ post-MVP с ЧЗ). |
| **Финансы** | Выручка ежедневно; финальные финансы раз в месяц (автокорректировка); баллы Ozon (1 балл = 1 ₽) — опционально. |
| **Ограничения** | Защита от автоакций (еженощно) — post-MVP. Разделение заказа — до загрузки этикеток. |

### 7.4. Направления и частоты обмена (MVP) `[INTEGRATIONS §принципы]`

| Данные | Направление | Частота |
|---|---|---|
| Карточки | система ↔ WB/Ozon (создание/импорт/матчинг) | по событию/кнопке |
| Цены | система → WB/Ozon | ежеминутно + после ручных изменений |
| Остатки FBS | система → WB/Ozon | при заказе/изменении + ночной импорт 00:00 МСК |
| Остатки FBO | WB/Ozon → система (только чтение) | по API (WB/Ozon) |
| Заказы FBS | WB/Ozon → система | автоимпорт ~раз в 2 мин; ручной; ночной |
| Этикетки | WB/Ozon → система (PDF) | по запросу |
| Статусы заказа | после отгрузки: система ↔ WB/Ozon | по событию |
| Финансы | WB/Ozon → система | WB еженедельно/ежедневно; Ozon раз в месяц (выручка — ежедневно) |

## 8. Phased roadmap / бэклог

Критический путь: **Foundation → Catalog+WB/Ozon → Stock+цены → Orders/сборка FBS
→ Этикетки/отгрузка → Аналитика → Hardening/бета**. T-shirt: S ≤ 1 нед, M ~2–3,
L ~3–5, XL ~5–8 (одна кросс-функциональная команда).

### Фаза 0 — Foundation (S–M)
**Эпики:** мультиарендный каркас (Account/Org/Warehouse); аутентификация
(регистрация, вход, сброс пароля, лимит сессий = 2); RBAC (4 роли); очередь
фоновых задач + retry/backoff; шифрование ключей (AES-256); AuditLog.
**User stories:** «Как селлер, я могу зарегистрироваться и создать организацию по
ИНН»; «Как админ, я могу завести сотрудника с ролью».
**Зависимости:** нет (старт).
**Exit criteria:** регистрация/вход работает; организация по ИНН создаётся;
фоновые задачи исполняются и ретраятся; ключи шифруются; аудит пишется.
`[onboarding §caps 1,11,13,16,23,24,28,37]`

### Фаза 1 — Каталог + интеграции WB/Ozon (L)
**Эпики:** PIM (3-уровневая модель, параметры, фото, ШК); адаптеры WB и Ozon
(аутентификация, импорт карточек с матчингом, публикация тумблерами); справочники
(бренды с `ozon_id`, производители, категории + mapping); статусы настройки
интеграций; уведомления о невалидных токенах; массовое редактирование Excel.
**User stories:** «Опубликовать карточку на WB и Ozon одним сохранением»; «Импорт
карточек из WB с автоматическим матчингом по ШК».
**Зависимости:** Фаза 0.
**Exit criteria:** карточка создаётся и публикуется на обоих МП с детальными
ошибками; импорт из WB/Ozon матчится в единую карточку; бренд Ozon привязывается
по ID; ≥ N карточек импортируются без потерь.
`[product-cards]`, `[integrations-marketplaces]`, WF-02

### Фаза 2 — Склад FBS + цены (L)
**Эпики:** склад FBS + связи со складами МП; перенос остатков; StockItem/Sku;
синхронизация остатков (раз в минуту + ночной импорт); мин/макс пороги; списание/
перемещение; история отправки; единая таблица цен; отправка цен (WB — скидка целым,
Ozon — цена+мин); минимальная цена-защита; история цен.
**User stories:** «Изменить остаток — улетает на WB и Ozon»; «Назначить цену на
оба МП с защитой от минуса»; «Перенести остатки с WB в систему».
**Зависимости:** Фаза 1 (нужны карточки + адаптеры).
**Exit criteria:** остатки синхронизируются с обоими МП (SLA после изменения ≤ 1
мин); расхождения фиксируются в истории; цена уходит на МП и ниже мин. не проходит;
сверка остатков доступна.
`[stocks-inventory]`, `[prices-strategies]`, WF-03, WF-08

### Фаза 3 — Заказы и сборка FBS (L–XL)
**Эпики:** импорт FBS-заказов (авто/ручной/с обновлением остатков); статусная
модель; резерв/списание; сопоставление «символ в символ»; поставка FBS; лента
заказов (фильтры, финансы, Excel); Лист сборки PDF; отметка собранными; закрытие
поставки (сверка для WB); возврат остатка после отмены.
**User stories:** «Собрать FBS-заказ от статуса Новый до закрытия поставки»; «Массово
отправить На сборку».
**Зависимости:** Фаза 2 (нужны остатки + резерв).
**Exit criteria:** полный цикл FBS-заказа проходит на WB и Ozon; статусы до отгрузки
не уходят на МП, после — синхронизируются; резерв корректно создаётся и
возвращается.
`[orders-assembly]`, WF-04

### Фаза 4 — Этикетки и отгрузка (M)
**Эпики:** печать этикетки заказа МП (PDF WB/Ozon); товарная этикетка (браузер/PDF);
шаблон товарной этикетки; «Загрузить этикетки» (WB — привязка к поставке; Ozon —
статус «Ожидает доставки»); закрытие поставки массово.
**User stories:** «Распечатать этикетки для поставки одним кликом».
**Зависимости:** Фаза 3.
**Exit criteria:** этикетки заказа и товарные печатаются для WB и Ozon; этикетка
становится доступна в правильном статусе; поставка закрывается.
`[orders-assembly §caps 8,9,10,19]`, Journey E/G

### Фаза 5 — Базовая аналитика/финансы (M)
**Эпики:** сбор MarketplaceOperation по API (WB/Ozon); базовый P&L (выручка,
себестоимость, комиссия, логистика, валовая прибыль/маржинальность); дашборд;
лента/график заказов; резервный ручной импорт отчётов.
**User stories:** «Вижу валовую прибыль по WB и Ozon за период».
**Зависимости:** Фазы 2–3 (нужны остатки/заказы/себестоимость).
**Exit criteria:** P&L сходится с ЛК МП в пределах допустимой дельты (см. §10);
дашборд обновляется по расписанию МП.
`[analytics-finance]` (урезанно), Journey H

### Фаза 6 — Hardening / закрытая бета (M)
**Эпики:** обработка лимитов API WB/Ozon (throttling, очереди, 429-backoff);
матчинг-тулз (объединение дублей, разрешение конфликтов); сверка остатков;
инструменты отладки (журналы ошибок импорта, «ошибки МП» в заказах); нагрузочное
тестирование синхронизации; bug-bash.
**Зависимости:** все фазы.
**Exit criteria:** метрики готовности MVP (см. §9) достигнуты на 3–5 пилотных
селлерах; надёжность синхронизации ≥ целевая.

## 9. MVP acceptance / метрики успеха

### 9.1. Functional acceptance (критерии готовности)
- ✅ Полный цикл FBS (Journey A→H) проходится на WB **и** на Ozon без ручных
  костылей.
- ✅ Публикация карточки на WB+Ozon одним сохранением; импорт с матчингом.
- ✅ Синхронизация остатков: после изменения остаток появляется в ЛК WB и Ozon
  (целевой SLA ≤ 1 мин для FBS-остатков).
- ✅ Цена уходит на оба МП; ниже минимальной не проходит; история цен/ошибок ведётся.
- ✅ Этикетки заказа и товарные печатаются для WB и Ozon.
- ✅ Базовый P&L формируется по обоим МП.

### 9.2. Технические метрики
- **Покрытие интеграций:** 100% ключевых операций WB и Ozon из §7 реализованы.
- **Надёжность синхронизации остатков/цен:** ≥ 99% успешно доставленных операций
  (с retry); доля неотработанных ошибок МП ≤ 1%.
- **Скорость:** автоимпорт FBS-заказов — латентность ≤ 2 мин; отправка цены/остатка
  ≤ 1 мин; загрузка страницы «Товары/Заказы» ≤ 2 с при 10k SKU.
- **Обработка лимитов API:** ни одного «провала» синхронизации из-за 429/throttling
  (очереди + backoff).
- **Матчинг:** ≤ 0,5% нераспознанных карточек при импорте с корректным ШК/артикулом.

### 9.3. Продуктовые метрики (после закрытой беты)
- **Активация:** % зарегистрировавшихся, дошедших до «импорт карточек + 1 публикация»
  (цель ≥ 60%).
- **Retention (W4):** % активных на 4-й неделе (цель ≥ 40%).
- **% заказов, собираемых через систему:** доля FBS-заказов WB+Ozon, доведённых
  до «Закрыто» внутри системы, а не в ЛК МП (цель ≥ 80%).
- **Время цикла сборки:** медиана от «Новый» до «Отправлен» (цель — короче, чем
  в ЛК МП).
- **NPS/CSAT пилотов** после фазы 6.

## 10. Риски и открытые вопросы

### 10.1. Технические риски

| Риск | Митигация |
|---|---|
| **Лимиты/квоты API WB и Ozon (429, throttling).** Точные лимиты в комплекте не приведены `[INTEGRATIONS §открытые вопросы 5]`. | Единая очередь фоновых задач per-tenant с приоритетами, экспоненциальный backoff,_BATCH-операции (массовые обновления), кэш токенов; отдельная фаза 6 на нагрузку. |
| **Матчинг карточек** WB↔Ozon в единую (расхождения артикулов/ШК, дубль/оригинал). | Единый ключ `unification_article+цвет+размер` и/или `barcode`; UI объединения/разъединения; тулз «Показать дубликаты»; журнал ошибок импорта `[stocks §cap 27–32]`, `[DATA_MODEL §Sku/StockLink]`. |
| **Расхождения остатков** SelSup↔МП (риск обнуления при первом импорте). | Первый импорт — только «Импорт заказов» (без обновления остатков); синхронизацию включать **только** после корректного переноса; сверка остатков `[orders §бизправила]`, `[stocks WF-1]`. |
| **Срок действия токенов WB** (ограничен) / отзыв. | Уведомления о невалидных токенах с переходом в настройки; документация по ротации `[integrations §cap 4]`. |
| **Ozon: заказ создаётся один раз и не редактируется; репрайсер недоступен.** | Строгий UX: «Создать заказ в Ozon» — только после упаковки; репрайсер/автоакции — post-MVP `[INTEGRATIONS §Ozon]`. |
| **Точные форматы API/Excel-шаблонов не описаны в комплекте.** | Реверс-инжиниринг эндпоинтов WB/Ozon и форматов массового редактирования — выделить в отдельный спайк в Фазе 1 `[INTEGRATIONS §открытые вопросы 1]`. |

### 10.2. Продуктовые риски
- **Сложность онбординга** (интеграции + перенос остатков + матчинг — много шагов).
  Митигация: мастер быстрого старта с чек-листом, автозагрузка аналитики за 2
  недели как «быстрая ценность» `[onboarding §cap 2]`.
- **Конкуренция с самими ЛК МП** — нужно чётко коммуницировать выигрыш «одно окно
  вместо двух» + валовую прибыль.
- **Биллинг отложен** — нужен фри-триал/лимиты на MVP, чтобы нести контролируемые
  затраты на API.

### 10.3. Регуляторные риски — Честный Знак
**Решение MVP:** **полный цикл Честного Знака (КИЗ, СУЗ, ввод/вывод из оборота,
ЭЦП/КриптоПро, УПД ДОП) — post-MVP.** Обоснование: требует УКЭП, регистрации в
ЧЗ/ГС1 РУС, подписания карточек Национального каталога, ЭДО — это отдельный
комплаенс-слой, нужный только маркируемым категориям (одежда/обувь/…)
`[marking-labels]`, `[WORKFLOWS WF-07]`.
**Митигация в MVP:** поле `category.flag_marked` + `tnved` + `gtin` в модели
(готовность); в UI — пометка «требует маркировки» и инструкция «действовать в ЛК
МП»; полный цикл — первый приоритет post-MVP.

### 10.4. Открытые вопросы (требуют решений/спайков)
1. **Точные лимиты API** WB и Ozon (RPS, квоты на публикацию/цены) — спайк.
2. **Форматы файлов** WB (акт приёмки, файл заказа, ШК коробов) и Ozon (грузоместа
   XLS) — нужны только в post-MVP (FBO), но проверить доступность API-аналогов.
3. **Глубина API** (3 мес WB/Ozon) — достаточна ли для онбординг-аналитики за 2
   недели? (Да, но фиксировать).
4. **Стратегия биллинга/лимитов MVP** (нет пробного периода в SelSup `[WF-01]` —
   как для нас?).
5. **Частота автоимпорта FBS-заказов** — в комплекте противоречие («раз в 2 мин»
   vs «раз в 15/30 мин» обновления) `[orders §открытые вопросы]` — зафиксировать
   целевой SLA ≤ 2 мин.
