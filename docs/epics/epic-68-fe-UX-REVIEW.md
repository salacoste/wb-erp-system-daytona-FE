## Общие UX-рекомендации по Epic 68

### 1. Информационная иерархия

**Принцип**: Progressive Disclosure (из front-end-spec.md)

Мониторинг — технически сложная страница. Ключевая задача UX — сделать её **понятной для бизнес-пользователя**, а не только для технического специалиста. Рекомендую трёхуровневую иерархию:

| Уровень | Что видит пользователь | Когда |
|---------|----------------------|-------|
| **L1 — Светофор** | Один индикатор: "Всё ОК" / "Есть проблемы" / "Критично" | Всегда (sidebar badge + первый экран) |
| **L2 — Обзор** | Health Score + карточки пайплайнов + полнота данных | Вкладка "Обзор" (default) |
| **L3 — Детали** | Heatmap, Telegram, Recovery, История | По навигации на конкретную вкладку |

**Ключевое UX-правило**: Пользователь НИКОГДА не должен уходить с дашборда, чтобы понять, есть ли проблемы. Индикация должна быть встроена в sidebar.

### 2. Sidebar-интеграция

**Рекомендация**: Добавить динамический badge в пункт "Мониторинг" в sidebar, аналогично badge в "Планирование" (urgentCount).

```
Мониторинг [●]     ← зелёная/жёлтая/красная точка (НЕ число)
```

**Обоснование**: Число алертов менее информативно, чем цветовой индикатор. Пользователь должен видеть статус системы **не заходя на страницу**. Точка-индикатор:
- `🟢` (hidden) — healthScore >= 80, нет алертов
- `🟡` — healthScore 50-79 или 1-2 алерта
- `🔴` — healthScore < 50 или 3+ алертов

### 3. Язык и тон

**Проблема в текущем эпике**: Терминология слишком техническая для целевой аудитории.

| Техническое (текущее) | Рекомендуемое (user-friendly) |
|-----------------------|------------------------------|
| Pipeline | Источник данных |
| Health Score | Состояние системы |
| Recovery | Восстановление |
| Heatmap | Карта активности |
| Data Completeness | Полнота данных |
| fbo_orders_sync | FBO Заказы |
| Task Execution | Выполнение задач |

**Правило**: В UI всегда использовать русские названия из колонки `displayName`, технические ID — только в tooltips или при hover.

### 4. Цветовая система

Текущая цветовая палитра в эпике корректна, но есть нюансы:

**Проблема**: 7 цветов в heatmap — слишком много для быстрого считывания. Пользователь не запомнит разницу между `missed` (gray-500) и `no_data` (gray-100).

**Рекомендация**: Группировка в 3 семантических кластера:
- **Позитивные** (не требуют внимания): success (green), recovered (emerald)
- **Требуют внимания**: partial (amber), pending (blue)
- **Проблемные**: failed (red), missed (gray-500)
- **Нейтральные**: no_data (gray-100) — визуально "пустая" ячейка

Добавить **легенду** под heatmap с образцами каждого цвета и описанием.

### 5. Адаптивность (Mobile)

**Приоритет**: Мониторинг — страница, которую часто проверяют с телефона ("Всё ли ОК?").

**Рекомендации по breakpoints**:
- **Mobile (<768px)**: Только L1 (светофор) + упрощённый L2 (список карточек вертикально). Heatmap недоступен — вместо него текстовый список проблем.
- **Tablet (768-1024px)**: Полный L2 + упрощённый heatmap (daily resolution only).
- **Desktop (>1024px)**: Полный функционал.

### 6. Accessibility (WCAG 2.1 AA)

**Критические требования** (поверх AC в историях):

1. **Цвет НЕ единственный индикатор**: Каждый цветовой статус дублируется текстом или иконкой. Например: `🟢 Работает`, `⚠️ Проблемы`, `❌ Критично` — не просто зелёный/жёлтый/красный круг.
2. **Heatmap**: Каждая ячейка должна быть focusable (tabindex), с aria-label: `"FBO Заказы, понедельник 10 февраля, статус: успешно, 96 из 96 выполнений"`.
3. **Контраст**: Amber (#F59E0B) на белом фоне — контраст 2.07:1, **НЕ проходит** AA. Использовать amber-600 (#D97706) — контраст 3.24:1 для large text, или добавить подложку.
4. **Screen reader**: Для Health Score gauge — `aria-valuenow`, `aria-valuemin=0`, `aria-valuemax=100`, `aria-label="Состояние системы: 95 из 100"`.
5. **Reduced motion**: Анимация gauge (заполнение кольца) должна учитывать `prefers-reduced-motion`.

### 7. Design Kit Compliance (`ui/`)

Все компоненты Epic 68 ДОЛЖНЫ визуально соответствовать Design Kit проекта:

| Элемент | Design Kit стандарт | Применение в мониторинге |
|---------|--------------------|-------------------------|
| **Primary Button** | Красный (#E53935), белый текст, rounded | "Восстановить", "Применить фильтр" |
| **Secondary Button** | Белая подложка, красная рамка | "Отмена", "Сбросить фильтры" |
| **Text Button** | Красный текст, без фона, underline on hover | "Подробнее", "Показать все" |
| **Active sidebar** | Красная полоска слева + красный текст | Пункт "Мониторинг" при активном маршруте |
| **Cards** | Белый фон, border, rounded-xl, shadow-sm, hover:shadow-md | Pipeline cards, Health Score, Telegram status |
| **Dropdown/Select** | Белый фон, красный highlight на выбранном | Фильтр пайплайнов, Period selector |

**Критично**: Кнопки в Recovery Panel (`Story 68.6`) — "Восстановить" = Primary Button (красный), "Отмена" = Secondary Button (outline). Кнопка "Принудительно" = destructive variant (красный + предупреждение).

## Рецензия по историям

### Story 68.1-FE: Маршрутизация и каркас

**UX-оценка**: Корректно, с дополнениями.

**Дополнения к AC**:

1. **Sidebar badge** (новый AC): Пункт "Мониторинг" в sidebar должен показывать цветовой индикатор здоровья (точку), обновляемый из dashboard polling. Иконка `Activity` из lucide-react — хороший выбор.

2. **Tab design**: Вместо 5 табов рекомендую 4:
   - "Обзор" (default) — объединяет Health Score + Pipeline Cards + Data Completeness + Telegram Quick Status
   - "Карта активности" (Heatmap)
   - "Восстановление" — объединяет Recovery + Data Recovery
   - "История"

   **Обоснование**: Telegram не заслуживает отдельной вкладки — quick status достаточен на "Обзор", а детали можно показать в expandable секции. 5 табов перегружают мобильную навигацию.

3. **Tab behavior on mobile**: На mobile (<768px) табы → вертикальный список (accordion-style), НЕ горизонтальный scroll. Горизонтальный scroll скрывает табы и пользователь может не знать, что они существуют.

4. **Breadcrumb**: Добавить breadcrumb `Dashboard > Мониторинг` для ориентации пользователя.

5. **Empty state**: Для нового кабинета показать не просто текст, а иллюстрацию (svg) + таймлайн: "Данные начнут поступать в течение 15-30 минут. Первый полный отчёт будет доступен через 24 часа."

### Story 68.2-FE: Health Score и статусы пайплайнов

**UX-оценка**: Хорошо продумано, критические дополнения ниже.

**Дополнения к AC**:

1. **Health Score gauge**: Рекомендую **полукруговой** (180°) gauge вместо полного кольца. Полукруг:
   - Занимает меньше вертикального пространства
   - Число внутри дуги читается лучше
   - Паттерн знаком из автомобильных приборных панелей

   ```
   ┌──────────────────────┐
   │     ╭━━━━━━━╮        │
   │   ╱           ╲      │  ← зелёная дуга
   │  ╱     95       ╲    │  ← число по центру
   │ ╱───────────────╲   │
   │ Система работает     │  ← текстовый статус под gauge
   │ 0 предупреждений     │
   └──────────────────────┘
   ```

2. **Pipeline cards — группировка**: Текущий wireframe корректен. Дополнения:
   - Внутри каждой карточки: **micro-sparkline** (последние 24 точки successRate) — визуально показывает тренд без клика
   - `lastSuccessAt` показывать как **относительное время**: "5 мин назад", "2 ч назад" — НЕ абсолютную дату
   - При `dataLagMinutes > expectedFrequency * 2` — пульсирующая анимация рамки (attention grab)

3. **Pipeline card click action**: При клике на карточку пайплайна — **НЕ переход**, а expand-секция под карточкой с: последние 5 выполнений, avg duration, error count. Переход на heatmap — через кнопку "Подробная история" внутри expand.

4. **Сортировка карточек**: Внутри каждой категории сортировать по severity: critical → warning → stale → healthy. Проблемные пайплайны должны быть наверху, чтобы пользователь сразу видел, что требует внимания.

5. **"Система работает" — недостаточно**: Добавить контекстную подсказку:
   - 80-100: "Все источники данных работают исправно"
   - 50-79: "Некоторые источники данных работают с задержками"
   - 0-49: "Обнаружены серьёзные проблемы с загрузкой данных"

### Story 68.3-FE: Heatmap пайплайнов

**UX-оценка**: Самая сложная история с точки зрения UX. Критические рекомендации.

**Дополнения к AC**:

1. **Date range picker**: Вместо произвольного выбора — **preset periods** с возможностью custom:
   - "Сегодня" | "7 дней" | "14 дней" | "30 дней" | "Выбрать период"
   - **Дефолт**: 7 дней (оптимальный баланс информативности и читаемости)
   - Preset-кнопки быстрее, чем date picker, для 90% use cases

2. **Resolution auto-switch**: Убрать ручной переключатель "По часам / По дням":
   - **1-3 дня**: автоматически по часам
   - **4-30 дней**: автоматически по дням
   - **Обоснование**: Пользователю не нужно думать о resolution — система сама выбирает оптимальное. Ручной переключатель добавляет когнитивную нагрузку.

3. **Heatmap cell size**:
   - Desktop: мин. 28x28px (touch-friendly даже на десктопе)
   - Tooltip при hover задержка: 200ms (предотвращает мигание при быстром перемещении мыши)
   - На mobile: ячейки 36x36px + tap вместо hover (tooltip как bottom sheet)

4. **Строки пайплайнов — sticky labels**: При горизонтальном скролле heatmap, названия пайплайнов (левый столбец) должны быть sticky (position: sticky, left: 0). Иначе при скролле пользователь теряет контекст, какая строка какому пайплайну соответствует.

5. **Summary bar вверху**: Текущий wireframe показывает "95 Health | 1234 выполнений | 5 ошибок | 99.6% успех" — это хорошо. Добавить:
   - **Trend indicator**: `↑ +2.3%` / `↓ -1.5%` по сравнению с предыдущим аналогичным периодом
   - Красным подсветить метрики, которые ухудшились

6. **Empty heatmap cells**: `no_data` ячейки (gray-100) не должны доминировать визуально. Для еженедельных пайплайнов (финансовый отчёт) большинство ячеек будут `no_data` — это нормально, но может выглядеть "пусто". Добавить пояснение: "Этот пайплайн запускается раз в неделю" рядом с row label.

7. **Filter chips**: Мультиселект фильтр пайплайнов — хорошо. Добавить preset-группы:
   - "Все" | "Высокочастотные" | "Ежедневные" | "Еженедельные" | "С проблемами"
   - "С проблемами" — фильтрует пайплайны, у которых есть хотя бы один failed/missed за период

### Story 68.4-FE: Полнота данных

**UX-оценка**: Хорошо структурировано. Дополнения:

1. **Progress bar семантика**: Использовать **segmented progress bar** вместо сплошного:
   - Каждый сегмент = 1 день
   - Заполненные сегменты = данные есть
   - Пустые сегменты = данные отсутствуют
   - Это даёт пользователю визуальное представление, КОГДА именно были пропуски, без необходимости expand

2. **Overall health indicator**: Вместо просто текста "Все данные загружены" — использовать тот же паттерн, что и Health Score, но упрощённый:
   ```
   Полнота данных: ████████░░ 94% — Незначительные пропуски
   ```
   - 100%: "Все данные загружены" (зелёный)
   - 90-99%: "Незначительные пропуски" (жёлтый)
   - <90%: "Требуется внимание" (красный)

3. **Expand interaction**: При expand строки показать таблицу пропущенных дат с:
   - Дата
   - Статус: "Можно восстановить" / "Истёк срок" (WB API retention)
   - Кнопка действия: "Восстановить" (одну дату) или "Восстановить все" (batch)
   - **Inline recovery result**: После нажатия "Восстановить" — показать результат прямо в строке (spinner → success/error), НЕ перенаправлять на вкладку Recovery.

4. **Table sorting**: Сортировать по completenessRatio ASC (наименее полные — наверху). Проблемные источники первыми.

### Story 68.5-FE: Telegram мониторинг

**UX-оценка**: Рекомендую упрощение.

**Основная рекомендация**: Telegram мониторинг НЕ заслуживает отдельной вкладки. Рекомендую:

1. **Quick status** — оставить на вкладке "Обзор" как компактную карточку (текущий wireframe хорош)
2. **Детальная панель** — показывать как **expandable section** на вкладке "Обзор", НЕ как отдельную вкладку
3. **Обоснование**: Telegram — вспомогательный канал уведомлений, а не core-функция мониторинга. Отдельная вкладка создаёт ложное впечатление о важности и увеличивает навигационную сложность.

**Если отдельная вкладка всё же нужна**, дополнения к AC:

1. **Bot status CTA**: Для `not_configured` — не просто текст, а полноценный CTA-блок:
   ```
   ┌────────────────────────────────────────┐
   │  🤖 Telegram-бот не настроен           │
   │                                        │
   │  Получайте мгновенные уведомления      │
   │  о проблемах с данными прямо в         │
   │  Telegram.                             │
   │                                        │
   │  [Настроить Telegram →]                │
   └────────────────────────────────────────┘
   ```
   Кнопка ведёт на `/settings/notifications` (существующий маршрут).

2. **Delivery stats визуализация**: Вместо таблицы цифр — **donut chart** (sent vs failed vs rate_limited vs quiet_hours). Числа менее информативны, чем пропорции.

3. **Event breakdown**: Добавить toggle "Показать отключённые" — по умолчанию показывать только enabled events, чтобы таблица была компактной.

### Story 68.6-FE: Восстановление данных

**UX-оценка**: Критическая история с точки зрения UX — пользователь выполняет ДЕЙСТВИЯ.

**Дополнения к AC**:

1. **Confirmation dialog**: Для ЛЮБОГО recovery action — confirmation dialog:
   ```
   ┌────────────────────────────────────────┐
   │  Восстановить данные?                  │
   │                                        │
   │  Задача: Рекламная статистика          │
   │  Период: 10.02 — 14.02.2026           │
   │                                        │
   │  Восстановление может занять           │
   │  несколько минут.                      │
   │                                        │
   │  [Отмена]          [Восстановить]      │
   └────────────────────────────────────────┘
   ```
   Для `forceRetry` — усиленный dialog с предупреждением: "Принудительное восстановление игнорирует cooldown и может создать нагрузку на API."

2. **Recovery progress**: После запуска recovery — показать inline progress:
   - Spinner + "Восстановление запущено..."
   - Через 5-10 секунд: "Задача в очереди. Обновим статус автоматически."
   - При следующем polling: обновить статус в таблице

3. **Recovery policy display**: Вместо показа raw policy (max_window, max_retries, cooldown) — человекочитаемые подсказки:
   - "Можно восстановить данные за последние 7 дней"
   - "Максимум 3 попытки, пауза 5 минут между попытками"
   - Показывать в tooltip при hover на "?" иконку

4. **Таблица сортировка**: По severity: critical → overdue → no_history → healthy. Кнопки действий — только для проблемных строк. Для healthy строк — кнопка серая/disabled с tooltip "Восстановление не требуется".

5. **Date range picker для recovery**: Добавить inline валидацию:
   - Максимальный период (из policy)
   - Предупреждение, если выбранные даты старше retention window WB API
   - "Данные старше N дней не могут быть восстановлены через API"

### Story 68.7-FE: История здоровья

**UX-оценка**: Хорошо для MVP. Дополнения:

1. **Timeline вместо ячеек**: Вместо ряда цветных ячеек — **timeline visualization** (вертикальная для mobile, горизонтальная для desktop):
   ```
   ── 🟢 ── 🟢 ── 🟡 ── 🟢 ── 🔴 ── 🟢 ── 🟢 ──
   Пн    Вт    Ср    Чт    Пт    Сб    Вс
                                  ▲
                           5 проблем
   ```
   Преимущество: timeline лучше передаёт хронологию, чем таблица.

2. **Detail modal**: При клике на день — НЕ modal, а **slide-over panel** (справа), чтобы пользователь видел таймлайн и детали одновременно:
   - Заголовок: "Пятница, 14 февраля 2026"
   - Summary: статус, количество проблем
   - Issues list с severity badges
   - Recommendations — actionable, с кнопками:
     - "Запустить восстановление" → переход на вкладку Recovery с предзаполненной датой
     - "Проверить настройки" → переход на Settings

3. **Period selector**: "7 | 14 | 30 дней" — хорошо. Добавить подсказку под selector:
   - Для 30 дней: "Загрузка может занять несколько секунд"
   - Для 7 дней: "(рекомендуется)" — чтобы направить пользователя к оптимальному варианту

4. **Trend summary**: Добавить однострочный trend summary над timeline:

## UX-паттерны для всего Epic 68

### Loading States

Для каждого компонента — **skeleton**, а не spinner:

```
┌──────────────────────┐    ┌──────────────────────┐
│  ████████████         │    │  Health Score: 95     │
│  ████████             │ →  │  Система работает     │
│  ██████████████       │    │  0 предупреждений     │
└──────────────────────┘    └──────────────────────┘
    Skeleton                     Loaded
```

**Правило**: Skeleton должен повторять layout загруженного компонента (одинаковая высота, ширина блоков). Не использовать generic spinner — он не даёт представления о содержимом.

### Error States

Три уровня ошибок:

1. **API timeout/network error**: Banner вверху страницы: "Не удалось загрузить данные мониторинга. [Повторить]". Показать последние известные данные (stale) с пометкой "Данные от 14:30".
2. **Partial error** (один endpoint упал): Показать данные, которые загрузились. Для упавшего блока — inline error: "Не удалось загрузить [блок]. [Повторить]".
3. **Auth error (401/403)**: Redirect на login / показать "Доступ запрещён" (как в эпике).

### Transitions и Animations

1. **Tab switch**: Fade transition (200ms) между вкладками. Не slide — мониторинг не имеет порядка "лево-право".
2. **Health Score gauge**: Анимация заполнения при первой загрузке (600ms ease-out). `prefers-reduced-motion` → без анимации.
3. **Pipeline card expand**: Height transition (250ms) с ease.
4. **Recovery action**: Button → spinner transition (immediate), success → green check (200ms fade).
5. **Polling update**: Новые данные появляются без перерисовки всей страницы. Если значение изменилось — кратковременная подсветка (highlight flash 500ms).

### Notifications Integration

Связка с существующей системой Telegram-уведомлений:

- Если пользователь настроил Telegram → на вкладке "Обзор" показать: "Вы получаете уведомления в Telegram @username"
- Если НЕ настроил → показать CTA: "Настройте Telegram-уведомления, чтобы получать алерты мгновенно"
- При critical health score → предложить включить Telegram, если не настроен
