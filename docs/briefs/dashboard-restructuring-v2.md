# Бриф: Реструктуризация дашборда — P&L нарратив

**Автор**: PM Agent
**Дата**: 2026-02-14
**Статус**: На ревью

---

## 1. Постановка проблемы

Текущий дашборд из 8 карточек не обеспечивает **целостное понимание финансового состояния бизнеса**:

| Проблема                                                     | Влияние                                                                 |
| ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Нет логики P&L (выручка → расходы → прибыль)                 | Пользователь не может за 10 секунд понять "сколько заработал"           |
| Нет метрики "К перечислению" (`payout_total`)                | Ключевой для бизнеса показатель — сколько WB перечислит на счёт         |
| Нет маржинальности (%)                                       | CFO не видит эффективность бизнеса в относительных показателях          |
| Два отдельных COGS (заказов, выкупов) без контекста          | Информация без P&L-потока не имеет смысла                               |
| "Теор. прибыль" — непонятный термин                          | Пользователь не понимает, что это за показатель и можно ли ему доверять |
| Заказы (шт.) занимают крупную карточку, а выручка — вторична | Приоритет метрик не соответствует потребностям CFO                      |

## 2. Пользовательские истории

### US-1: Финансовый директор — P&L за 10 секунд

> Как **финансовый директор**, я хочу **видеть полную P&L-картину на одном экране**, чтобы **за 10 секунд оценить финансовое состояние бизнеса за неделю**.

### US-2: Предприниматель — сколько заработал

> Как **владелец бизнеса**, я хочу **видеть валовую прибыль и маржу с индикацией достоверности**, чтобы **понимать, сколько я реально заработал и можно ли этим данным доверять**.

### US-3: Операционный директор — заказы и логистика

> Как **операционный директор**, я хочу **видеть объём заказов, расходы на логистику и хранение с % от продаж**, чтобы **оценить операционную эффективность**.

### US-4: CFO — расходная структура

> Как **финансовый директор**, я хочу **видеть все категории расходов (комиссии, логистика, хранение, реклама) с долей от выручки**, чтобы **выявлять аномалии и оптимизировать расходы**.

### US-5: Предприниматель — сумма к перечислению

> Как **владелец бизнеса**, я хочу **видеть точную сумму к перечислению от WB**, чтобы **планировать кэшфлоу и оплату поставщиков**.

## 3. Предлагаемая структура карточек (10 карточек, 5 секций)

### Информационная архитектура: P&L-нарратив

```
Секция 1: ВЫРУЧКА (откуда деньги)
  → Секция 2: РАСХОДЫ WB (куда уходят деньги на площадке)
    → Секция 3: К ПЕРЕЧИСЛЕНИЮ (сколько получишь)
      → Секция 4: СЕБЕСТОИМОСТЬ И РЕКЛАМА (твои расходы)
        → Секция 5: ПРИБЫЛЬ (итог)
```

## 5. Таблица дневной разбивки

### Предлагаемые колонки

| Колонка       | Источник                      | Формат     | Сортировка |
| ------------- | ----------------------------- | ---------- | ---------- |
| Дата          | —                             | DD.MM (Пн) | По дате    |
| Заказы, шт    | `orders/trends` → ordersCount | `123 шт.`  | Числовая   |
| Сумма заказов | `orders/trends` → revenue     | `45 678 ₽` | Числовая   |
| Реклама       | `advertising` daily           | `12 345 ₽` | Числовая   |

### Убираемые колонки

- ~~COGS заказов~~ — нет daily finance, данные неполные
- ~~COGS выкупов~~ — нет daily finance breakdown
- ~~Выкупы~~ — нет daily finance breakdown
- ~~Логистика~~ — нет daily finance breakdown
- ~~Хранение~~ — нет daily finance breakdown
- ~~Теор. прибыль~~ — невозможно посчитать без daily finance

### Graceful degradation

- Недоступные данные → `—` (тире), не `0`
- Колонка скрывается если все значения `—`
- Ошибки API не ломают другие колонки

## 6. Критерии приёмки

### AC-1: Структура сетки

- [ ] 10 карточек в 5 секциях по 2
- [ ] Секции визуально разделены отступами
- [ ] Адаптивность: 2 колонки (desktop) → 1 колонка (mobile)

### AC-2: Корректность данных

- [ ] Все 10 карточек отображают данные из правильных API-полей (см. секцию 4)
- [ ] Формула "Комиссии WB" = сумма 6 полей
- [ ] "Хранение и приёмка" = `storage_cost + paid_acceptance_cost`
- [ ] "К перечислению" = `payout_total`

### AC-3: Сравнение с предыдущим периодом

- [ ] Каждая карточка показывает бейдж ▲/▼ и %
- [ ] Зелёный = улучшение, красный = ухудшение
- [ ] Для маржинальности — сравнение в п.п.

### AC-4: Субтитлы с контекстом

- [ ] Расходные карточки: "X% от продаж"
- [ ] Продажи: "Выкупы X ₽ — Возвраты Y ₽"
- [ ] Себестоимость: покрытие с цветовой индикацией
- [ ] Реклама: "ROAS: X,Xx"

### AC-5: Условная логика прибыли

- [ ] `cogs_coverage >= 80%`: прибыль и маржа отображаются
- [ ] `cogs_coverage < 80%`: "Заполните себестоимость" + ссылка на COGS
- [ ] При coverage 80-99%: жёлтое предупреждение

### AC-6: Акцентные карточки

- [ ] "К перечислению" и "Валовая прибыль" визуально выделены
- [ ] Увеличенный шрифт, акцентная рамка

### AC-7: Daily breakdown

- [ ] 4 колонки: Дата, Заказы шт, Сумма заказов, Реклама
- [ ] Убраны колонки без данных

### AC-8: Форматирование

- [ ] Валюта: `1 234 567,89 ₽`
- [ ] Проценты: `15,5%`
- [ ] п.п.: `+2,3 п.п.`

## 8. Технические заметки

### Маппинг API-полей

```typescript
// Комиссии WB — агрегация 6 полей
const wbCommissionsTotal =
  finance.commission_sales_total +
  finance.acquiring_fee_total +
  finance.loyalty_fee +
  finance.penalties_total +
  finance.wb_commission_adj +
  finance.wb_services_cost;

// Хранение и приёмка
const storageAndAcceptance =
  finance.storage_cost + finance.paid_acceptance_cost;

// % от продаж
const pctOfSales = (value: number) =>
  finance.sale_gross > 0 ? (value / finance.sale_gross) * 100 : 0;
```
