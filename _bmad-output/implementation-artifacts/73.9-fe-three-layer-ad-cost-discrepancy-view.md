# Story 73.9: Three-Layer Ad Cost Discrepancy View

Status: done

## Story

As a **seller managing advertising budgets**,
I want **to see three layers of ad costs side-by-side (platform spend, corrected spend, actual WB deduction)**,
so that **I can identify discrepancies and understand the true cost of advertising**.

## Acceptance Criteria

1. **AC-1: Delta rendering** — Given platform spend=100K, actual deduction=95K, When view renders, Then shows both with delta "−5 000 ₽ (−5,0%)"
2. **AC-2: Yellow warning** — Given discrepancy >5%, When delta renders, Then highlighted in yellow warning color (#F59E0B)
3. **AC-3: Red alert** — Given discrepancy >10%, When delta renders, Then highlighted in red (#EF4444)
4. **AC-4: Info explanation** — Given user clicks info icon, When explanation expands, Then describes why platform and actual costs differ (rounding, timing, corrections)

## Dev Notes

### Three-Layer Data Architecture

| Layer | Source | Hook | Field | Update Freq |
|-------|--------|------|-------|-------------|
| Layer 1 | PromotionAPI (`adv_daily_stats.spend`) | `useAdvertisingAnalytics()` | `summary.total_spend` | Daily |
| Layer 2 | Backend reconciliation (TBD) | N/A — not yet implemented | N/A | TBD |
| Layer 3 | Weekly report (`wb_finance_raw.wb_promotion`) | `useFinancialSummary()` | `wb_promotion_cost_total` | Weekly |

**Layer 2 is TBD** — implement as disabled/placeholder column. Show "Скорректированная стоимость (скоро)" with muted styling.

**Known discrepancy**: `ad_spend` ≠ `wb_promotion` is normal. Difference sources:
- Rounding at different aggregation levels
- Timing: daily API vs weekly report finalization
- WB corrections applied after report generation
- Typical diff: ~73 RUB on normal spend levels (validated Feb 2026)

### Data Fetching Strategy

**Problem**: Advertising uses date range (`from`/`to`), finance uses ISO week (`YYYY-Www`).

**Solution**: The advertising page already has `dateRange.from` and `dateRange.to`. For Layer 3:
- Use `useFinancialSummary(weekString)` where `weekString` covers the ad date range
- If range spans multiple weeks → use `useMultiWeekFinancialSummary(weeks[])` and sum `wb_promotion_cost_total`
- Week calculation: `getISOWeek()` from `date-fns` on the `from`/`to` dates
- **Critical**: If range doesn't align to full weeks, show info tooltip explaining partial week coverage

**Alternatively** (simpler): Fetch advertising summary total_spend for Layer 1 (already fetched by parent page — reuse `data?.summary?.total_spend`), and fetch finance-summary for the **last completed week** in the date range for Layer 3. Show "(данные за неделю YYYY-Www)" label.

### Info Section Content (AC-4)

From `docs/DATA-SOURCES-REFERENCE.md` and MEMORY:

> **Почему суммы различаются?**
>
> Расход по рекламному кабинету (Платформа) и удержание в еженедельном отчёте (Факт) могут расходиться по нескольким причинам:
> - **Округление**: Данные округляются на разных уровнях агрегации
> - **Таймлаг**: Рекламный кабинет обновляется ежедневно, а отчёт формируется еженедельно
> - **Корректировки**: WB может вносить итоговые поправки при закрытии отчётного периода
> - **Нормальный порог**: Расхождение до 3-5% считается нормальным

### Previous Story Learnings (73.8-FE)

1. **ESLint 200-line limit is strict** — estimate file sizes before writing, use atomic full-file writes
2. **Russian locale** for all user-facing text
3. **Extract data formatters to config/utils** — don't duplicate across components
4. **useMemo dependency granularity**: extract sub-properties (e.g., `data?.items`) before using as deps
5. **useEffect not useMemo for side effects** — useMemo for pure computations only
6. **String split for date formatting** — avoid `new Date()` constructor on date-only strings (timezone issues)
7. **Toast only on transition** — use useRef guard for one-time notifications
8. **Conditional data fetching** — use `enabled` option on hooks when data only needed for toggle state
9. **Loader2 spinner** — use from lucide-react for inline loading indicators
