## Dev Notes

### Proven Extraction Patterns (from Stories 74.1-74.4)

**Barrel Re-Export Pattern** (preserves consumer API):
```typescript
// Original file becomes thin re-export
export { funcA, funcB } from './extracted-file'
export { funcC } from './other-extracted-file'
export type { TypeA } from './extracted-file'
```
This ensures consumers keep importing from the same path — no codebase-wide import updates needed.

**Pure Utility Split** (74.2, shared/calculate-margin-stats.ts):
```typescript
// Pure data/config files do NOT need 'use client'
export const STATUS_CONFIG = { ... } as const
export function getStatusColor(status: string) { ... }
```

### Critical Rules

1. **NEVER change functionality** — this is pure structural refactoring
2. **Pure lib files do NOT need `'use client'`** — these are all pure logic/data, no React hooks
3. **Don't duplicate types** — import from source (74.2 code review finding)
4. **Run tests after EACH file split** — don't batch validation
5. **File size limit is 200 lines** — ESLint enforced, no exceptions
6. **Extracted files also ≤200 lines** — don't just move the problem
7. **Barrel re-exports preserve consumer API** — AC #4 critical
8. **Keep files well under 200** — aim for 150-180 to leave headroom
9. **Internal (non-exported) helpers**: When splitting, only export what's needed for cross-file imports. Don't make everything public unnecessarily.

### Special Case: WB_STATUS_CONFIG (Task 4)

The `WB_STATUS_CONFIG` object in `wb-status-mapping.ts` is a **304-line pure data const** mapping WB status codes to display properties. It cannot fit in a single 200-line file.

**Strategy**: Split the status entries by category group into 2 data files:
- File 1: `creation` + `seller_processing` + `warehouse` + `logistics` categories
- File 2: `delivery` + `cancellation` + `return` + `other` categories + `UNKNOWN_STATUS_CONFIG`
- File 2 exports the merged `WB_STATUS_CONFIG` combining both halves
