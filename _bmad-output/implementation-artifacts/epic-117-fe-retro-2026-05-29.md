## What Went Well

### W-1 — Orchestrator-split for true bidirectional Pattern 1 (Story 117.1)
The original spec proposed wiring the chart into `SearchOrdersTab` between cards and table, but that would have left the chart inside the tab's query-fetch early-returns — a query error would have blanked the chart, violating AC-3's "vice versa" clause. Implementation split the tab into a 29-line orchestrator + `SearchOrdersOverview` (123 lines, prior tab body verbatim) + `SearchOrdersChart` (149→185 lines after fixes). Both fail independently, both tested (Pattern 1 graceful-degradation in BOTH directions). **Architectural lesson**: "independent state machines" means parent early-returns blank siblings too — orchestrator-split, not just child-self-fetch, is required for true bidirectional Pattern 1.

### W-2 — Verify-first paid off massively (Story 117.2)
Branch A was the predicted outcome of the 3-way decision matrix, but the evidence had to be live. Cabinet `f75836f7-c0bc-4b2c-823c-a1f3508cce8e`, `GET /v1/analytics/search/orders` summary `{totalSearchOrders, searchOrderShare}` and items `{key, totalOrders, uniqueProducts}` — no revenue. **The backend docs (`API-PATHS-REFERENCE.md` orderBy=totalRevenue + test-api response examples) are aspirational/stale.** Story 91.1-FE was right; the docs are not. Without the live verification we'd have rebuilt revenue columns on a wrong premise, and Story 117.4 wouldn't have re-scoped to orders ranking.

### W-3 — Defensive Frontend Principle applied with contextual nuance
Same principle, opposite stance, both correct: `toChartRows` (117.1) **coerces** numeric/string keys via `String(item.key)` because the chart axis is purely visual; `pickTopByOrders` (117.4) **filters** non-string keys because the query renders as a user-facing label. Both decisions documented inline in the source. **The principle isn't "always coerce" or "always filter" — it's "don't fabricate; choose based on consumption context."**

### W-4 — DOM-query test harness for recharts proven again
`AdCostDiscrepancyChart.test.tsx` set the precedent (Epic 73-FE); Story 117.1 confirmed it: **no `vi.mock('recharts')` required**. jsdom renders `.recharts-responsive-container` as a real DOM node; assert on that + `role="img"` + aria-label. The "matchMedia is not a function" jsdom flake in Story 117.1 first test run got caught and guarded with `typeof window.matchMedia !== 'function'`; 18/18 passed on retry. The harness is portable across analytics charts.

### W-5 — Pure-functions-over-hook-mocking convention scaling
Every Epic 117 story extracted a testable pure function: `toChartRows`/`formatDayTick` (117.1), `resolveSellerDisplayName` (117.3), `pickTopByOrders` (117.4). Pure-fn tests are ~3-4× cheaper than component tests and they document the contract. Story 117.4 ended with 6 pure-fn + 7 component tests; if everything had been hook-mocked, the same coverage would have cost ~13-15 component tests.

### W-6 — Mid-epic re-scope authority preserved velocity (Story 117.4)
Re-scoped from "Top Keywords by Revenue" → "Top Keywords by Orders" on the same day Story 117.2 closed. Sprint-status commit `ccbf3ee` recorded the pivot. No story-spec-thrashing, no Epic 117 stop-the-world. **Empirical evidence > original plan** is the kind of mid-epic agility verify-first stories enable.

### W-7 — Codifications from Epic 118-FE dogfooded by Epic 117-FE source-code stories within 24 hours
- **Story 117.2 sprint-status drift** = exact within-line YAML propagation sub-pattern Story 118.1-FE A-5 codified; caught by user-invoked `/code-review 117.2`.
- **Stories 117.3 + 117.4 close-row Lessons** = used A-6 dual-attestation ("N at close-row-write-time; N+1 after this row's Lessons line ticks the count") as standard within 24 hours of Story 118.1-FE codifying it.
The codifications self-validated across epic boundaries.

## Key Insights

### I-1 — Pattern 4 generalizes beyond codification stories
Pre-Epic-117 expectation framed Pattern 4 (fix-block propagation drift) as a codification-context defect. Story 117.4 Pass-2 = 100% Pattern 4 findings on a pure source-code story. The discipline operates correctly regardless of story type; fresh-context Pass-2 is the only reliable countermeasure. **Implication**: do NOT relax 2-pass discipline for source-code work assuming Pattern 4 won't fire.

### I-2 — Mechanism B (user-invoked post-close `/code-review`) is not codification-exclusive
5/5 codification stories + 2/2 source-code stories that received user-invoked post-close `/code-review` surfaced substantive findings. Story 117.1 = 5 findings (1 MED reuse, 4 LOW), Story 117.2 = 1 MED (within-line YAML drift on its own sprint-status entry). The mechanism's value for source-code stories: catches cross-story carry-fixes + within-line YAML drift on the story's own tracking entry. **Empirically, Mechanism B generalizes across story types.**

### I-3 — Verify-first stories have asymmetric upside
Story 117.2's Branch A discovery:
- Resolved a 6-month-old 91.1-FE-vs-backend-docs conflict permanently
- Prevented Story 117.4 from being built on a wrong premise (revenue ranking)
- Filed Backend Request #175 as a side observation
- Cost: ~3 SP for a doc-only ship

If even one of those outcomes had been missed by skipping verification, the rework cost would have been multiples of the verification cost. **Verify-first should be a story-template option for any backend-doc-vs-FE-type conflict** (action item A-1).

### I-4 — Codifications dogfooded across epic boundaries validate fastest
Story 118.1-FE shipped A-5 (within-line YAML) + A-6 (dual-attestation) codifications. Within 24 hours:
- Story 117.2 sprint-status entry **demonstrated** the exact A-5 sub-pattern (caught by user-invoked review)
- Stories 117.3 + 117.4 **adopted** A-6 dual-attestation as standard close-row practice

The cross-epic dogfooding pattern (codification in Epic N, application in Epic N-1's source-code stories closing concurrently) is a strong signal of codification quality. **Future codifications should plan for cross-epic application validation, not just intra-epic.**

### I-5 — Boundary Normalizer gaps tax every defensive-coding decision in their module
Story 117.1's `toChartRows` and Story 117.4's `pickTopByOrders` each had to make a contextual coerce-vs-filter decision because the `/orders` endpoint lies about its shape (`key: string | number` per types, but no normalizer enforces). The decisions are correct, but the cognitive overhead was real. Closing the Boundary Normalizer gap in Epic 119 Story 1 removes this tax from every future search-analytics story.

## Significant Discoveries

### SD-1 — Backend reference docs are aspirational, not authoritative
`docs/API-PATHS-REFERENCE.md` (line 6716 lists `totalRevenue` as valid search orderBy) + `test-api/34-search-analytics.http` (response examples with revenue fields 75000.0 etc.) **both describe a shape the live backend does not produce.** Story 117.2 live verification was the only way to detect this — pre-flight grep alone would have re-introduced revenue columns based on stale docs. **Implication**: backend reference docs require periodic live-verification audits; trust live response > backend docs > FE types in that order.

### SD-2 — searchOrderShare can exceed 100% (`394.23` observed)
Live `/v1/analytics/search/orders` for cabinet `f75836f7` returned `searchOrderShare: 394.23` — a "share" should be ≤100%. Filed as part of Request #175. Existing UI renders it as `formatPercent` → "394.2%" which is misleading but out-of-scope for Story 117.2 (revenue scope). **Defensive Frontend principle violation by current code** — noted for Epic 119 follow-up alongside the by-product/by-query 500s.
