### Enrichment Fix: Remove 200-Product Cap

**Current problem**: `useProducts({ limit: 200 })` at BuyoutTable.tsx:55 caps product name resolution to first 200 products. Backend API max per-page is 200 (cursor-based pagination).

**Fix approach**: Create a `useAllProducts()` hook or inline `useQuery` that fetches ALL product pages:
```typescript
// In BuyoutTable.tsx or a shared hook
const { data: productsData } = useQuery({
  queryKey: ['products', 'all-for-enrichment'],
  queryFn: async () => {
    const allProducts: ProductListItem[] = []
    let cursor: string | undefined
    do {
      const params = new URLSearchParams({ limit: '200' })
      if (cursor) params.append('cursor', cursor)
      const response = await apiClient.get<ProductListResponse>(
        `/v1/products?${params.toString()}`
      )
      allProducts.push(...response.products)
      cursor = response.pagination.next_cursor
    } while (cursor)
    return allProducts
  },
  staleTime: 120_000, // 2 min — enrichment data doesn't change often
})
```

**Alternative (simpler)**: If catalog is typically <500 products, just fetch 2-3 pages:
```typescript
// Option B: Parallel fetch of first 3 pages (covers up to 600 products)
const page1 = useProducts({ limit: 200 })
const page2 = useProducts({ limit: 200, cursor: page1.data?.pagination?.next_cursor })
// Merge results
```

**Recommended**: Use the `useQuery` approach with cursor loop — it's clean, handles any catalog size, and avoids chained hook calls.

**Important**: The `useProducts` hook is generic (supports filters, search, etc.). For enrichment, we only need nm_id → name/brand/vendorCode mapping. A dedicated enrichment query is cleaner.

### Backend Fallback

`BySkuBuyoutItem` already has backend-provided fields:
- `productName: string | null` — product name from WB data
- `brand: string | null` — brand from WB data
- `supplierArticle: string | null` — vendor code

Current enrichment pattern in BuyoutTable.tsx:
```typescript
{item.supplierArticle || product?.vendorCode || '—'}  // vendorCode
{product?.saName || item.productName || '—'}            // product name (prefer enriched saName)
{item.brand || product?.brand || '—'}                   // brand
```

This pattern should be preserved — products API `saName` is preferred over backend's `productName`.
