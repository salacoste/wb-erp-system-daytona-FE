# Story 76.5: Confirm + Recalculate + Readonly View

Status: done

## Story

As a **seller**,
I want to confirm a shipment to lock in costs, and recalculate if COGS change,
So that my delivery cost snapshots are frozen for accounting and can be updated when needed.

## Acceptance Criteria

1. **Confirm button** — Given a DRAFT shipment, a "Подтвердить" button is visible in the header actions (after "Рассчитать"). Clicking it calls `POST /v1/shipments/:id/confirm` with body `{ confirmedBy: user.email }`. On success, the shipment query is invalidated/refetched, and a toast displays "Отправка подтверждена". Button shows loading state during the request. If the server returns 400 with validation errors, display them via the existing `ValidationErrorPanel` (same as calculate flow from 76.4).
2. **CONFIRMED readonly state** — When `shipment.status === CONFIRMED`, all mutation controls are disabled/hidden: edit button, delete button, calculate button, add/remove pallet, add/remove box line. The header shows a "ПОДТВЕРЖДЕНА" badge with a lock icon (already done in 76.2). Cost snapshot data from the last calculation is displayed via `CalculationResults`.
3. **Recalculate button** — Given a CONFIRMED shipment AND user role is `Owner`, `Manager`, or `Service` (NOT `Analyst`), a "Пересчитать" button is visible. Clicking it calls `POST /v1/shipments/:id/recalculate` (empty body). On success, updated cost results display and the shipment query is invalidated/refetched. Shipment remains CONFIRMED.
4. **Analyst role restriction** — Given a CONFIRMED shipment AND user has `Analyst` role, the "Пересчитать" button is hidden. No recalculate functionality is exposed.
5. **Auto-calculate on confirm** — The backend `/confirm` endpoint auto-calculates before confirming. If validation errors occur, a 400 response is returned with the same error structure as `/calculate`. Frontend extracts and displays these errors, and confirmation is blocked.
6. **Conflict handling** — If confirm returns 409 (already confirmed), show an appropriate error message and refetch the shipment to sync state.
7. **Component extraction** — ShipmentDetailHeader.tsx is at 195 lines. Adding confirm/recalculate will exceed 200-line limit. Extract action buttons into a new `ShipmentActions.tsx` sub-component. All files ≤ 200 lines, 0 ESLint errors, 0 TypeScript errors.
8. **Hook additions** — Add `useConfirmShipment` and `useRecalculateShipment` to `src/hooks/use-shipment-calculations.ts`. Both follow existing mutation pattern with dual cache invalidation.

## Dev Notes

### Architecture Patterns (MUST follow)

**API functions** — Add to existing `src/lib/api/shipment-cost/shipment-calculations-api.ts`:
```typescript
import type { Shipment, CalculateShipmentResponse } from '@/types/shipment-cost'

export async function confirmShipment(
  shipmentId: string,
  confirmedBy: string
): Promise<Shipment> {
  return apiClient.post<Shipment>(
    `/v1/shipments/${shipmentId}/confirm`,
    { confirmedBy }
  )
}

export async function recalculateShipment(
  shipmentId: string
): Promise<CalculateShipmentResponse> {
  return apiClient.post<CalculateShipmentResponse>(
    `/v1/shipments/${shipmentId}/recalculate`
  )
}
```

**Hooks** — Add to existing `src/hooks/use-shipment-calculations.ts`:
```typescript
export function useConfirmShipment(shipmentId: string) {
  const queryClient = useQueryClient()
  return useMutation({
    mutationFn: (confirmedBy: string) => confirmShipment(shipmentId, confirmedBy),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: shipmentsQueryKeys.byId(shipmentId) })
      queryClient.invalidateQueries({ queryKey: shipmentsQueryKeys.all() })
    },
  })
}

export function useRecalculateShipment(shipmentId: string) {
  const queryClient = useQueryClient()
  return useMutation({
    mutationFn: () => recalculateShipment(shipmentId),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: shipmentsQueryKeys.byId(shipmentId) })
      queryClient.invalidateQueries({ queryKey: shipmentsQueryKeys.all() })
    },
  })
}
```

### Error Handling Patterns

**Confirm error handling** — Reuse the same `ApiError` extraction pattern from 76.4:
```typescript
async function handleConfirm() {
  onCalculateStart?.() // Clear stale results
  try {
    const user = useAuthStore.getState().user
    await confirmAsync(user?.email ?? '')
    toast.success('Отправка подтверждена')
  } catch (err: unknown) {
    if (err instanceof ApiError && err.status === 400) {
      // Extract validation errors same as calculate flow
      const data = err.data as { errors?: Array<{ errorCode: string; message: string; affectedIds?: (string | number)[] }> } | undefined
      if (data?.errors?.length) {
        const mapped: ValidationError[] = data.errors.map(e => ({
          code: e.errorCode,
          message: e.message,
          affectedIds: e.affectedIds?.map(String),
        }))
        onCalculateError?.(mapped)
        return
      }
    }
    if (err instanceof ApiError && err.status === 409) {
      toast.error('Отправка уже подтверждена')
      refetch() // Sync state
      return
    }
  }
}
```

### Anti-Patterns to Avoid

1. **Do NOT add buttons directly to ShipmentDetailHeader** — it's at 195 lines, extract to ShipmentActions first
2. **Do NOT use `useAuthStore.getState()` in render** — use selector `useAuthStore(s => s.user?.role)` for reactivity
3. **Do NOT call `refetch` from auth store** — use the `refetch` from `useShipment` hook in the detail page
4. **Do NOT create separate state for recalculate results** — reuse the same `calcResults` state from page.tsx (same `CalculateShipmentResponse` shape)
5. **Do NOT implement optimistic updates** for confirm — must refetch after server confirms
6. **Do NOT hardcode user email** for `confirmedBy` — read from `useAuthStore(state => state.user?.email)`
7. **Do NOT forget `aria-label`** on confirm/recalculate buttons
8. **Do NOT exceed 200 lines** in any file — ShipmentActions must stay under 200
9. **Do NOT import `ApiError` in ShipmentActions** — the error extraction handler pattern should be passed via callbacks from ShipmentDetailHeader or defined in ShipmentActions
10. **Do NOT implement role-based routing** — only hide the recalculate button; the backend returns 403 as a safety net
11. **Do NOT create types for ConfirmShipmentRequest** — just pass `confirmedBy: string` as param to API function
12. **Do NOT use `vi.doMock()`** in tests — use mutable variable + getter in `vi.mock()` factory

### Previous Story Intelligence (76.4)

Key learnings from Story 76.4 code review:
- **`ValidationError.code` is `string`** (not enum) — raw backend codes are mapped via `BACKEND_CODE_MAP` in `normalizeCode()` at display time
- **`ApiError` class** at `src/types/api.ts` — has `.status` (number) and `.data` (unknown). Thrown by apiClient on non-OK responses
- **Error extraction pattern**: `err instanceof ApiError && err.status === 400` → `err.data as { errors?: Array<...> }` → map to `ValidationError[]`
- **`onCalculateStart` callback** clears stale results/errors before new operation — reuse for confirm too
- **`src/hooks` is a symlink to `src/hooks-v1`** — same directory, not duplicates
- **Dual cache invalidation** — Always invalidate both `byId(shipmentId)` AND `all()` in mutations
- **Component barrel exports** — Update `src/components/custom/shipments/index.ts` for new components
- **Mutable mock variable pattern** — For test mocking: `let mockX = false` with getter in `vi.mock()` factory
