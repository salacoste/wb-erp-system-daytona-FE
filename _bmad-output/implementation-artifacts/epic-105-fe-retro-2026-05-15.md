## What Went Well

### S-1: Both stories converted a discipline into automation in one epic
Anti-Pattern #8 had 6+ recurrences across Epics 87-104 despite explicit codification — manual catch was the bottleneck. Pre-flight verification was a 5-story empirical pattern (103.1-3 + 104.1 + 104.3 = ~11 SP of duplicate work avoided) but lived only in author intuition. Both now have structural enforcement: ESLint rule + workflow step. Each future epic gets the benefit without the discipline tax.

### S-2: User chose option (a) "ratchet + allowlist" for Story 105.1 — pragmatic phase
The strict-rule-then-fix-everything approach (option b) would have produced a 30-50 file diff with potential downstream regressions. Option (a) ratchets the rule in for new code only, leaving existing violations as a documented follow-up backlog. Locks the discipline immediately; defers the cleanup to focused future work. This is the standard "baseline reset" pattern from Epic 99-FE / Epic 100-FE.

### S-3: ESLint rule covers both direct + optional-chain access via 4 paired selectors
A naïve selector would miss `item?.revenue ?? 0` (the optional chain wraps in `ChainExpression` per TypeScript ESLint parser). The executor's 4-selector design covers both forms × both pattern families (root names + suffix patterns). The self-test includes optional-chain fixtures (`roas_optchain`) to lock this behavior.

### S-4: Pre-flight workflow step has explicit branches for all 3 outcomes
The 3-branch structure (all SHIPPED / all UNIMPLEMENTED / partial) is explicit rather than implicit. Story 4.5's logic is clear: if ALL ACs are satisfied, `goto step="9"` to close as no-op. Partial branch narrows scope rather than re-implementing. This makes the discipline self-documenting in the workflow XML itself.

### S-5: Citation baseline held through significant file growth
Story 105.1's 25 file modifications + Story 105.2's workflow XML edit didn't introduce any new broken citations. The 22-citation baseline (down from 24 after Epic 104-FE) survived. Discipline of section-name citations over line-number citations (Story 97.2-FE) is paying compound returns.

## What Didn't Go Well

### C-1: Two-repo monorepo structure required manual coordination
The ESLint rule lives in the root `eslint.config.js` (monorepo parent), but the allowlists live in `frontend/src/**/*` (nested frontend repo). Two separate `git commit` operations were needed, with the parent commit local-only pending separate push decision. The pattern works but adds cognitive overhead. Documented in Epic 105 spec but the asymmetry is a recurring papercut for any cross-repo work.

### C-2: 66 pre-existing violations is a substantial follow-up backlog
The allowlist approach (option a) defers a real cleanup. Each of 66 `eslint-disable-next-line` comments encodes "this might be wrong, but we're not fixing it now." Without a tracked follow-up story, this backlog can stay frozen indefinitely. Story 105.X follow-up exists in name but not yet in sprint-status. Risk: drift into permanent debt.

### C-3: Executor's report got truncated mid-sentence
The executor agent's final response cut off at "9/9 self-tests pass. Now update CLAUDE.md Anti-Pattern #8:" — never finished the report including commit hash. Recovery via `git status` + `git log` + manual gate verification took ~5 minutes of extra context. Not a code defect but a tooling/agent UX issue. Story 104-FE retro action A-4 (hook heuristic tightening) is related — the same agent UX layer has rough edges.

### C-4: Pre-flight Step 4.5 isn't unit-tested
The workflow XML edit is prose + structure — no automated test that the "skip to Step 9" branch fires correctly when ACs are all SHIPPED. Future workflow regressions could silently disable the pre-flight discipline. The dev-story workflow itself has no test harness; testing would require a meta-workflow that exercises dev-story against fixture stories. Out of scope for Story 105.2 but a real gap.

### C-5: Self-test script for Story 105.1 lives outside vitest
`scripts/test-anti-pattern-8-rule.sh` is a shell script invoking `eslint` against tempdir fixtures. It's effective but doesn't run automatically in CI (no `npm test` integration). If someone breaks the rule selector later, they have to remember to run the shell script manually. Could be wrapped in a vitest test that shells out — but adds complexity. Defer to follow-up.

## Lessons Learned

1. **Two-pass review discipline empirical evidence for automation case** — Anti-Pattern #8's 6+ recurrence chain proves the same thing Story 97.7-FE proved for HALT scripts: prose enforcement has empirically high skip rate, automated lint/structural enforcement has high catch rate. The case generalizes: if a discipline is codified BUT recurs ≥3 times, automate it. This epic adds a 7th data point to the chain. (Story 105.1)
2. **Optional-chain AST nodes need explicit selector handling** — TypeScript ESLint parser wraps `?.` in `ChainExpression`, so a selector targeting `MemberExpression > LogicalExpression` misses optional-chain forms. Paired selectors (direct + ChainExpression) are mandatory for full coverage. This is the kind of subtlety where `RuleTester` / self-test fixtures earn their keep. (Story 105.1)
3. **"Ratchet + allowlist" is the right starting move for retroactive lint rules** — when adding a new rule to existing code, ERROR-level + allowlist existing is reversible and ships immediately. Fix-everything-first risks downstream regression and indefinite delay. The follow-up cleanup is a separate (smaller) decision. (Story 105.1 user choice a)
4. **Pre-flight verification deserves a workflow step, not just a guideline** — the discipline was documented in CLAUDE.md after Epic 104-FE retro but only got enforced when added as Step 4.5 in dev-story workflow. Workflow steps fire automatically per story; CLAUDE.md prose only fires if read. Encode discipline at the point of enforcement, not just the point of documentation. (Story 105.2)
5. **Branch-aware workflow logic prevents wasted re-implementation** — the 3-branch structure (all SHIPPED / all UNIMPLEMENTED / partial) is more useful than a binary "verify y/n" flag. The "partial" branch is where most stories will actually land — saving the explicit narrowing as a workflow output captures the discovery in the story file. (Story 105.2)
